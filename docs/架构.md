# 架构说明

> 这份文档讲**为什么这么设计**，以及"新增一个东西该放哪"。使用层面的操作看 [README](../README.md) 和 [使用指南](框架使用指南.md)。

## 1. 框架的定位

一个 **clone 下来就能写业务** 的桌面应用骨架：分层、IPC、配置、日志、主题、多语言、路由、测试与门禁都已经接好。

明确的**非目标**（不是"以后做"，是不做）：

| 不做            | 原因                                                                 |
| --------------- | -------------------------------------------------------------------- |
| 自动更新        | 更新源与发布渠道属于使用方（[路线图第 13 节](framework-roadmap.md)） |
| 代码签名 / 公证 | 证书归每个开发者（[第 14 节](framework-roadmap.md)）                 |
| 内置遥测 / 埋点 | 采集什么数据是业务决策（[第 15 节](framework-roadmap.md)）           |

支持平台：**Windows 10+ 与 Linux**。macOS 代码保留但未验证、不发布。

## 2. 四层结构与依赖方向

```
┌─────────────────────────────────────────────┐
│ renderer   Vue 3 + Pinia + Router           │
│            只能通过 window.electronAPI 出圈  │
└──────────────────┬──────────────────────────┘
                   │ 白名单 + 类型契约
┌──────────────────▼──────────────────────────┐
│ preload    contextBridge 暴露的最小 API 面   │
│            sandbox: true，不能加载相对分块    │
└──────────────────┬──────────────────────────┘
                   │ ipcRenderer.invoke
┌──────────────────▼──────────────────────────┐
│ main       Electron 主进程：窗口/模块/IPC     │
│            拥有完整 Node 能力                 │
└──────────────────┬──────────────────────────┘
                   │ 纯数据（无 electron 依赖）
┌──────────────────▼──────────────────────────┐
│ shared     类型契约 / 常量 / 默认配置 / 文案  │
└─────────────────────────────────────────────┘
```

依赖是**单向**的：`renderer → preload → main`，`shared` 被三者共用但不反向依赖任何人。

几条硬约束，违反了会在类型或运行时炸：

- `shared/` 下的模块**不能 import electron**，否则渲染进程一旦引用就会崩。
  `shared/utils/index.ts` 现在只依赖 `fs`，渲染端可以安全从 `@shared/utils` 根导入（早期版本因为它 import 了 `dialog` / `app`，只能引 `helpers` 与 `path`）。
- `renderer/` 不能 import `main/` 的任何东西（vite 也解析不到）。
- `preload` 把白名单**内联**在文件里，不 import 共享常量：开 `sandbox` 后 preload 无法 require 相对路径分块。

## 3. 一次 IPC 调用的完整链路

以"读取配置"为例：

```
ConfigPanel.vue
  → useConfigStore().ensureLoaded()
  → window.electronAPI.invoke('config:get')          ← 类型：IpcInvokeMap['config:get']
  → preload：allowedChannels.has('config:get')       ← 运行时闸门（防误用）
  → ipcRenderer.invoke
  → ipcMain.handle('config:get')
  → isTrustedSenderUrl(event.senderFrame.url)        ← 运行时闸门（防伪造来源）
  → 模块贡献的 handler（ConfigModule.ipcHandlers）  ← 通道由模块自己声明
  → ConfigHandler.getConfig(event)
  → ConfigModule.getConfig()                         ← 返回副本，防外部改内部状态
  → 结构化克隆回渲染进程
```

契约由三处共同保证，缺一不可：

| 位置                               | 作用                                  | 漏了会怎样                                |
| ---------------------------------- | ------------------------------------- | ----------------------------------------- |
| `shared/types` 的 `IpcInvokeMap`   | 声明通道名 + 参数元组 + 返回类型      | 调用处编译失败                            |
| `preload` 的 `ALLOWED_CHANNELS`    | 运行时白名单                          | 编译期断言失败（漏加会 `typecheck` 报错） |
| `ipc.manager` 的 `registerHandler` | 聚合注册 + sender 校验 + 重复通道拦截 | 运行时找不到通道或启动时报重复            |

**跨 IPC 只能传纯数据。** Vue 的 `ref` / `reactive` 是 Proxy，结构化克隆无法复制，会抛
`An object could not be cloned.`。所以渲染端发复杂对象前要过 `renderer/utils/plain.ts` 的 `toPlain`。

## 4. 启动链路（顺序有意义）

`src/main/index.ts`（入口：单实例锁、进程级异常）与 `src/main/app.ts`（启动序列）：

```
Windows: 清理残留/只读 lockfile（只删无进程持有的）
单实例锁 requestSingleInstanceLock
  ↓ 失败：exit 21（启动器据此区分「有实例」与「锁文件不可用」）
读取 .env：SECURITY_SANDBOX_ENABLED=false → appendSwitch('no-sandbox')（必须在 ready 前）
new App()
  ├─ initLogger()            ← 先建日志，后面所有模块都能落盘
  ├─ WindowManager / ModuleManager / IpcManager 实例化（此时还不碰 app API）
app.whenReady()
  ├─ Windows: setAppUserModelId
  ├─ ModuleManager.init()
  │    ├─ 核心模块 ConfigModule（required：失败即中断启动）← 读取 .env 并映射为 AppConfig
  │    └─ 用户模块 userData/modules/*.cjs（失败只隔离自身）
  ├─ windowManager.setConfigModule()   ← 建窗要读 window 尺寸/位置
  ├─ ipcManager.setupHandlers()        ← 需要 ConfigModule 实例
  ├─ 权限请求默认拒绝
  ├─ applyApplicationMenu()            ← 开发者工具项由配置决定
  ├─ createMainWindow()
  │    ├─ show: false → ready-to-show 才显示（避免白屏）
  │    ├─ loadApp：process.defaultApp ? localhost:5173 : resources/dist/index.html
  │    ├─ 导航守卫 + DevTools 守卫
  │    └─ 按 .env 的 WINDOW_* 建窗（离屏坐标丢弃，运行时不回写）
  └─ 启动打点（ready / modules / ipc / window / total）
before-quit：destroy 模块（3 秒超时）→ flush 日志 → quit
```

启动顺序由 `src/main/app.test.ts` 守护；窗口事件（关闭到托盘、通知、导航守卫）由 `managers/window.manager.test.ts` 覆盖。

关键点：

- **ConfigModule 必须先于建窗**：窗口尺寸、托盘文案都读它。
- **开发态判断用 `process.defaultApp` 而不是 `app.isPackaged`**：Electron 45 下用 `electron .` 启动时 `isPackaged` 也可能为 true。

## 5. 配置：`.env` 是唯一来源

```
项目根 .env（打包后 resources/.env）
   ↑ 解析（支持注释 / export / 引号）
main/utils/env.ts
   ↑ 映射 + 类型校验（非法值回退默认值并 warning）
shared/config/from-env.ts → shared/config/defaults.ts（唯一默认值）
   ↓
main/modules/config.module.ts ── config:get ──→ renderer/stores/config.store.ts（只读）
```

- **没有写入路径**：`config:update` 已移除，也没有 `config.json`；`userData` 下只保留日志等运行时数据。
- **只读的原因**：配置在启动前就要决定沙箱与窗口尺寸，运行时改配置无法即时生效，反而制造「设置页显示已保存、重启后回退」的假象。改配置 = 编辑 `.env` + 重启。
- **测试/CI 可用 `ELECTRON_ENV_FILE` 指向临时文件**；开发态 `electron:dev` 监听根目录 `.env`，变化后自动重启 Electron。
- **为什么不用 `dotenv`**：只需要键值对解析这几十行，自己写可完全控制 BOM、注释与回退行为，也少一个依赖。

## 6. 日志与错误处理

```
main:
  logger.ts         文件写入（异步串行队列 + flush）
  app-logger.ts     进程级单例：initLogger 前回退 console
  所有模块          getLogger().info/warn/error   ← 统一进 userData/logs/main.log

renderer:
  main.ts errorHandler / unhandledrejection
  AppErrorBoundary  渲染期异常兜底，不让整页白屏
  utils/report.ts   reportError → invoke('log:report')

main/ipc/log.handler.ts  级别白名单 + 2000 字符截断 + 10 秒 50 条限流
```

两个设计取舍：

- **渲染端不直接写文件**：写文件能力一旦开放，配合 `userData/modules` 的自动加载就是持久化 RCE。日志走 IPC，由主进程落盘。
- **退出前 flush**：`before-quit` 与 `uncaughtException` 都先 `flush()` 再退出，崩溃原因不会停在缓冲区。

## 7. 模块系统

```
Module { name, version?, description?, init(): Promise, destroy?(): Promise, ipcHandlers?() }
```

- 核心模块 `required: true`，初始化失败中断启动。
- 核心模块可用 `ipcHandlers()` 声明自己提供的 IPC 通道；`IpcManager` 只做聚合、sender 校验与重复通道拦截。
- 用户模块在 `userData/modules/*.{cjs,js}`，逐个 `require`，失败只记日志、不影响其它模块；**不参与 IPC 贡献收集**，避免磁盘插件覆盖核心通道。
- 用户模块只能 `require('electron')` 与 Node 内置模块：打包时排除了 `node_modules`（[插件开发](插件开发.md) 有说明）。
- 插件日志通过 `globalThis.__frameworkLogger` 交给它们，否则只能 `console.log` 打不到文件。

## 8. 安全模型

威胁假设：**渲染进程可能被攻破**（XSS、被注入的第三方脚本、恶意 DevTools 扩展）。

渲染进程被攻破后，能做什么 / 不能做什么：

| 能力                     | 状态      | 依赖的防线                                           |
| ------------------------ | --------- | ---------------------------------------------------- |
| 访问 Node API            | ❌        | `nodeIntegration: false` + `sandbox`（默认开启）     |
| 直接调任意 IPC           | ❌        | preload 白名单 + `IpcInvokeMap`                      |
| 从伪造来源调 IPC         | ❌        | sender 按 `URL.origin` 精确比对                      |
| 任意读写文件             | ❌        | 框架**不提供**文件通道                               |
| 写插件目录实现持久化 RCE | ❌        | 同上（这是移除 `file:*` 的直接原因）                 |
| 污染配置、注入未知键     | ❌        | 配置只读，渲染进程没有写入通道                       |
| 打开 DevTools 改状态     | 生产态 ❌ | 菜单项由 `FEATURE_DEVELOPER_TOOLS` 控制 + 快捷键拦截 |
| 外链跳转 / 新开窗口      | ❌        | `will-navigate` + `setWindowOpenHandler`             |
| 加载远程脚本             | ❌        | CSP `script-src 'self'`                              |

**已知边界（不是缺陷，是范围）**：

- 插件本身拥有主进程完整权限，`userData/modules` 里放什么就执行什么——信任问题由使用方解决。
- DevTools 收口是防误触与防"用户手滑"，不是防有本地权限的攻击者。
- 未签名产物会被 SmartScreen / Gatekeeper 拦，这是发布决策，框架不管。

## 9. 扩展点：新增东西该放哪

| 我要加…        | 放这里                                           | 还要改                                                                            |
| -------------- | ------------------------------------------------ | --------------------------------------------------------------------------------- |
| 一个页面       | `renderer/views/Foo.vue`                         | `router/routes.ts` 注册懒加载                                                     |
| 一个 IPC 通道  | `main/ipc/foo.handler.ts`                        | `constants` + `types` + 所属核心模块的 `ipcHandlers()` + `preload` 白名单（4 处） |
| 一个配置项     | `shared/config/defaults.ts`                      | `types` + `schema` + 需要 UI 就加 `ConfigPanel` + 文案进 `shared/i18n`            |
| 一个功能开关   | `types` 的 `FeatureFlags`                        | 同上五步，见 README「新增一个功能开关」                                           |
| 一个主进程模块 | `main/modules/foo.module.ts`                     | `module.manager.ts` 注册（核心模块用 `required: true`）                           |
| 一种语言       | `shared/i18n` 加一份 `AppMessages`               | `SUPPORTED_LOCALES` + `ConfigPanel` 的选项                                        |
| 一个主题色     | `renderer/styles/theme.css` 变量                 | 组件里**不要**写死颜色                                                            |
| 一条日志/异常  | `getLogger()`（主进程）/ `reportError`（渲染端） | —                                                                                 |
| 一个测试       | 与被测文件同目录 `*.test.ts`                     | 组件测试文件头加 `@vitest-environment jsdom`                                      |

## 10. 关键取舍记录

| 决策       | 选择                    | 原因                                                                       |
| ---------- | ----------------------- | -------------------------------------------------------------------------- |
| 路由模式   | hash                    | 打包后 `loadFile` 走 `file://`，history 模式会 404                         |
| IPC 返回   | 直接返回数据            | 曾经包过 `{success, data}` 信封，但 handler 里立刻拆包，从未跨进程，纯样板 |
| 配置校验   | 手写 schema             | 零依赖、能裁剪未知键、错误信息带键路径；引入 zod 会让模板多一个依赖        |
| 配置存储   | 自己写 JSON 文件        | 需要原子写、串行化、未知键迁移，都要可控                                   |
| 主进程构建 | `build.ssr: true`       | 非 SSR 构建会把 `process.env` 替换成 `{}`，环境变量静默失效                |
| 渲染端产物 | 拆 vendor 块            | 业务改动不让框架层 hash 变化                                               |
| 主题实现   | CSS 变量 + `data-theme` | 组件不用各写一套 dark 样式                                                 |

## 11. 质量门禁的分工

| 门禁                    | 能挡住什么                                     | 挡不住什么                    |
| ----------------------- | ---------------------------------------------- | ----------------------------- |
| `typecheck`             | 类型契约、IPC 参数、白名单漏加                 | 运行时行为                    |
| `lint` / `format:check` | 风格与粗心错误                                 | 逻辑错误                      |
| `test`（126 用例）      | 纯函数、配置模块、IPC 注册、组件渲染、插件加载 | 真实 IPC 序列化、真实窗口行为 |
| `build`                 | 打包期错误、CSP 注入、分块                     | 运行时崩溃                    |
| `smoke`                 | 应用起不来、配置/日志不落盘                    | 界面交互                      |
| `e2e`                   | 真实 IPC 链路（配置保存、主题、语言）          | 托盘等窗口级行为              |

**教训**：所有把 `invoke` mock 掉的单测都放过了 `An object could not be cloned.`——凡是涉及跨进程传参的改动，必须在本地跑 `npm run e2e`。
